CalisHealth — Survey Management → Onboarding → Level Result

Step by step: what the Content Manager / Admin does, how the System reacts, and what the Member experiences — from configuring the level benchmark and creating survey steps, to finishing the survey and receiving a level + recommended plan.

🔑 Two rules keep this flow simple:
1. The level is scored from the benchmark table (Level & Benchmark Criteria), not from survey logic in the survey screen.
2. The Level test step is generated automatically: the benchmark rows define it (PUSH_UP_MAX_REPS, PLANK_MAX_SECONDS…), nobody types those questions by hand.

PHASE 0Content Manager sets the level benchmark — the "answer key"/admin/benchmark-criteria

0.1 Opens Level & Benchmark Criteria

  • Sets which exercises are tested (system REPS / HOLD exercises only)
  • Sets the 1-point max and 2-point max per exercise → 3 bands
  • Names the levels and their contiguous score ranges (N → 3N)
  • Presses Save All Changes

0.2 Validates, then writes in one transaction

  • 1–8 distinct system exercises · intermediateMax > beginnerMax
  • Names unique · ranges contiguous, start at N, end at 3N
  • ≥ 1 level stays ACTIVE · fallback ids/status valid
  • Saves thresholds on the 3 oldest levels (cut-offs are shared, so renames don't break them)
saved400 with a fixable message, nothing saved
Member not involved yet — this is the answer key the survey will later ask for.

0.3 Never edits the Level test by hand

the survey follows the table automatically

0.4 BenchmarkSurveySync rewrites the Level test step

  • New exercise → creates the NUMBER question (required, integer, 0–500 reps / 0–1800 sec, unit, card config)
  • New question → linked to step LEVEL_TEST
  • Removed exercise → already answered ⇒ link deactivated (history kept); never answered ⇒ link deleted
  • Locks the survey row, bumps step.revision → other admins get 409 STEP_MODIFIED
member sees exactly the configured exercises

1.7 Set the rules

Required, validation rules (integer, min/max), options, and conditional display ("show only when…").

1.9 Save changes (Update step)

1.10 One transaction, all-or-nothing

  • Optimistic lock: revision mismatch → 409 STEP_MODIFIED

  • Status rule: no ACTIVE → DRAFT; ACTIVE needs ≥ 1 visible question
  • Removed question with answers ⇒ deactivate link; without ⇒ delete link

1.12 Shows exactly the member view

PHASE 2The member takes the survey/survey/*

2.1 Logs in, lands on the survey

2.2 Resolves the session, in priority order

  • IN_PROGRESS session exists → continue it (answers kept)
  • Newest is SKIPPED → resume to IN_PROGRESS, same version, answers kept
  • Newest is COMPLETED and no retake → straight to /survey/result
  • Otherwise start: new session pinned to the ACTIVE version; only one IN_PROGRESS per member
version-pinned ⇒ later content edits never disturb a member mid-survey

2.3 Answers step by step, presses Continue

Can go back, close the tab, or Skip survey and resume later.

2.4 Saves each step atomically

  • Known codes, no duplicates, value present, question really shown in that step
  • Each value checked by its question-type handler (range, integer-only, option belongs to bank…)
  • Conditions: answering a hidden question is rejected (QUESTION_NOT_APPLICABLE)
  • Any error → 400 SURVEY_VALIDATION_FAILED, "nothing was saved"
  • null clears a previous answer

2.5 Takes the Level test

One number input per benchmark exercise — exactly what Phase 0 configured.

2.6 Presses Finish

2.7 Completion gate — re-validates the whole survey from the DB

Every active, applicable question must be valid; answers to no-longer-applicable questions must be cleared. Otherwise 400 SURVEY_INCOMPLETE, session stays IN_PROGRESS.
PHASE 3System scores the level and builds the plan — inside the same transactionLevelAssessmentService
—

3.1 Scoring source of truth, in order

  • Survey's own rule set (if ACTIVE and valid) → LevelRuleEvaluator → method RULES
  • Otherwise the benchmark table: each exercise → 1 pt (≤ beginner max) / 2 pts (≤ intermediate max) / 3 pts (above)
  • Total = Σ points, max = N × 3 → level whose [scoreMin, scoreMax] contains it (nearest ACTIVE level if that range is inactive)
  • Zero rule: any 0 reps/seconds ⇒ forced to the lowest active level
  • Unbalanced rule: best − worst ≥ 2 points ⇒ drop one level
  • Fallback: no/invalid rule set or unscorable ⇒ the Result step's fallback level (reason NO_RULE_SET/RULES_INVALID)
—

3.2 Builds the recommended plan

  • Reads desired sessions/week from the member's answer (1–7)
  • Matches an ACTIVE DailyPlanTemplate for level + days/week
  • Spreads sessions across the week (MON, WED, FRI…), attaches exercises
  • Weeks / sessions / minutes shown per the Result step config

3.3 Persists everything

  • survey_level_results: 1 row per session (method, level, total, breakdown JSON) — re-scoring updates it
  • Session → COMPLETED with completedAt
  • Profile ← level, weight, height, gender, goal, days/week
  • Weight + height ⇒ BMI + first member_body_metrics row
started tracking on day one
PHASE 4Result, plan preview & starting training/survey/result

4.1 Sees the result screen

  • Level badge + "Level k of N"
  • Breakdown: total "6 of 9 points", a human summary, and per exercise: value, points, band ("20–40 reps")
  • Recommended plan card: name, weeks, sessions/week, minutes/session, weekly rhythm

4.2 Serves the stored result

Only for a COMPLETED session → else 409 SESSION_NOT_COMPLETED. Legacy sessions are scored once under a row lock so parallel requests can't double-score.
—

4.3 Preview training plan

Weekly rhythm, each session's name, exercises with sets / reps / duration.

4.4 Read-only modal data

Nothing is written; only shown when the Result config allows the preview.
—

4.5 Start my training plan

4.6 Confirms the plan onto the profile

Requires COMPLETED + a scored result + a plan → else SESSION_NOT_COMPLETED / RESULT_NOT_AVAILABLE / PLAN_NOT_AVAILABLE. Writes level + sessions/week, returns the plan snapshot.

4.7 Sent to the dashboard to train

onboarding complete

4.8 Detours

  • Back to level test → reopen
  • Retake survey → brand-new session
  • Come back later → result re-readable

4.9 Reopen semantics

Only a COMPLETED session; refuses if another session is in progress (409 ACTIVE_SESSION_EXISTS). Deletes the stored result so the next finish re-scores from scratch; answers stay intact. A retake keeps the old session + result in history.

4.10 Profile already carries level & weekly rhythm

Who writes what — one-glance map

  1. Content Manager → benchmark exercises + thresholds + level names/ranges (Phase 0).
  2. System → the Level test questions (*_MAX_REPS / *_MAX_SECONDS), generated by the sync, kept in step LEVEL_TEST.
  3. Admin / Content Manager → steps, order, questions, conditions, statuses, and result_config (breakdown, preview, weeks, sessions, minutes, fallback level).
  4. Member → answers, including the level test numbers.
  5. System → level + breakdown + plan; profile fields and the first body metric.
  6. Member → previews the plan, starts it, optionally reopens the level test.
