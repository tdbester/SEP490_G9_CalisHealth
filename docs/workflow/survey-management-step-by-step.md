# Survey Management → Onboarding → Level Result (Step-by-Step Business Workflow)

> Scope: from the moment the **Content Manager sets the level benchmark**, through **Admin/Content Manager creating survey steps**, to a **new member completing the onboarding survey** and **receiving the level + recommended plan**, all the way to **previewing / starting the plan**.
> Every step below is named after what the actor does, and then what the system does in response (validations, locks, DB writes). Screens and endpoints are taken from the current code.

---

## Cast

| Actor | Where they work | What they own |
|---|---|---|
| **Content Manager** | `/admin/benchmark-criteria` | The **Level & Benchmark Criteria** table: which exercises are tested, the 1/2/3-point thresholds, the level names and their score ranges. **This table is the single source of the level result.** |
| **Admin / Content Manager** | `/admin/surveys` (Survey management) | The **steps** of the onboarding survey: order, questions, conditions, statuses, and the **Result step configuration** (what the result screen shows + fallback level). |
| **System** | Spring Boot services | Validates, locks, versions, syncs the level-test questions, scores the level, builds the plan, syncs the member profile. |
| **New Member** | `/survey/*` → `/survey/result` | Answers the survey, takes the level test, sees the result, previews and starts the plan. |

Two ideas keep the whole flow sane:

1. **Levels are scored from the benchmark table, not from the survey.** The survey only carries the *questions* that collect the reps/seconds.
2. **The Level test step is generated by the benchmark table.** The Content Manager never hand-writes those questions; the system keeps the step in sync (`BenchmarkSurveySync`).

# PHASE 0 — Content Manager sets the level benchmark (the "answer key")

| # | Content Manager does | System does |
|---|---|---|
| 0.1 | Opens **Level & Benchmark Criteria** | `GET /api/content/level-benchmarks` → returns three blocks: configured **exercises + thresholds**, the **available system exercises** (REPS / HOLD only), and the **levels** with their score ranges. |
| 0.2 | Presses **Add exercise** and picks an exercise from the system library | Frontend restricts the picker to the same category; a REPS exercise scores in *reps*, a HOLD exercise in *seconds*. |
| 0.3 | Types the **1-point max** (beginner) and **2-point max** (intermediate) for that exercise | Nothing yet — the two limits define 3 bands: `≤ 1-point max` = 1 pt, `≤ 2-point max` = 2 pts, above = 3 pts. |
| 0.4 | Adds / renames / reorders / removes **levels** | Frontend keeps ranges **contiguous** live: the first level starts at `N` (N = number of exercises), the last ends at `3N`, each minimum = previous maximum + 1. Adding a level makes the widest level give up 1 point; removing a level hands its points to the neighbour. |
| 0.5 | Presses **Save All Changes** | `PUT /api/content/level-benchmarks`. |

**What the system validates before writing anything** (`LevelBenchmarkService.validateRequest`):

- 1 to 8 exercises, all different, all **system** exercises with category `REPS` or `HOLD`, reported category must match the real one.
- Thresholds positive and `intermediateMax > beginnerMax`.
- At least one level; every level id exists and is distinct; names unique; name ≤ 50 chars; `scoreMin ≥ 0`; `scoreMax ≥ scoreMin`; status `ACTIVE`/`INACTIVE`; **at least one level stays ACTIVE**.
- Score ranges contiguous, starting exactly at `N` and ending exactly at `3N`.

Any failure → **400** with a message the Content Manager can act on; **nothing is saved**.

**Then it writes, in one transaction:**

1. Deletes the old benchmark threshold rows, upserts the levels (existing ids first so renames can free a name, then new ones).
2. Re-saves the thresholds on the **three oldest levels** (`threshold_holder`) — the cut-offs are shared by every level, this is only a storage detail, so renaming/reordering levels never affects them.
3. Calls **`BenchmarkSurveySync.sync(configured, removedSlots, actor)`**.

**What `BenchmarkSurveySync` does — this is the bridge to the survey:**

| Situation | System behaviour |
|---|---|
| New exercise added | Creates the survey question in the bank if missing. Its **code = the "slot"**: `<EXERCISE_NAME>_MAX_REPS` or `_MAX_SECONDS` (e.g. `PUSH_UP_MAX_REPS`, `PLANK_MAX_SECONDS`). Type `NUMBER`, required, integer only, `0..500` reps / `0..1800` sec, unit `reps` / `sec`, with a card-style display config (label, hint, icon). |
| Question already exists but is `INACTIVE` | Switches it back to `ACTIVE` and fills in a missing display config. Existing text is never overwritten. |
| Question not yet linked to the Level test step | Links it to the step whose code is **`LEVEL_TEST`**, appending it at the end of the step order. |
| Exercise removed from the table | If members already answered that question → the link is only **deactivated** (answers stay readable). If nobody answered → the link is deleted. The question itself stays in the bank. |
| Any of the above changed the step content | Locks the survey row (`SELECT … FOR UPDATE`), bumps **`step.revision`** and `updatedAt/updatedBy` → an Admin who had the step open gets **409 STEP_MODIFIED** instead of overwriting blindly. |

**Net effect:** the member's Level test always shows exactly the exercises and thresholds on this table. Nobody has to touch Survey management for it.

# PHASE 1 — Admin / Content Manager builds the survey steps

Entry point: **Survey management** (`/admin/surveys`), working on the **ACTIVE** version of `CALISHEALTH_ONBOARDING` (or the newest **DRAFT** if there is no active one). An **ARCHIVED** version is read-only.

### Step 1 — Open the page

| Admin | System |
|---|---|
| Opens **Survey management** | Loads the step list of the resolved version: survey code/name/version/status, status counters (**All / Active / Draft / Inactive**), and each step's position, question count, question types, last update, revision. Drag-and-drop is only enabled on **All** with no search, because *Save order* must send **every** step. |

### Step 2 — **Create step**

| Admin | System |
|---|---|
| Presses **Create step**, types a name, an optional description, an optional code, and picks the type (**Questions** by default, or **Result**). Can pick questions right away, from the bank or written new. | `POST /api/content/surveys/{code}/steps` → **locks the survey row FOR UPDATE** (concurrent edits queue up instead of colliding; an ARCHIVED version → **409 SURVEY_ARCHIVED**). Then: |

System checks and writes:

1. **Name unique** in this survey (case-insensitive) → else **409 STEP_NAME_EXISTS**.
2. **Code**: given or auto-generated from the name (`BODY_INFORMATION`, Vietnamese diacritics stripped, `_2`, `_3` on collision) → duplicate → **409 STEP_CODE_EXISTS**.
3. **Status is always `DRAFT`** — a new step is invisible to members until published.
4. **Placement**: a QUESTIONS step is inserted **immediately before the Result step**; the Result step is always kept **last**.
5. A **Result** step gets `ResultConfig.defaults()`; a survey can only have **one** Result step (**409 RESULT_STEP_EXISTS**), and it **cannot contain questions** (**400 RESULT_STEP_NOT_EDITABLE**).
6. Questions sent along are resolved first (see Step 4). Any error → **nothing is written**.

### Step 3 — **Add questions**

| Admin | System |
|---|---|
| Presses **Add question** and picks from the bank, or presses **New question** and writes one. | Bank picker = only `ACTIVE` questions **not already used in another step of this survey** (one question appears once per survey). The list flags questions **already answered by members** (their type/content become locked) so the Admin does not silently break history. A brand-new question is validated per type by the question-type handler (code uniqueness, text, options, rules). |

### Step 4 — **Set the rules**

| Admin | System |
|---|---|
| Marks a question **Required** (or leaves it inheriting the bank default), edits validation rules (integer, min/max…), option lists, and adds **conditional display**: "show this question only when *that* question's answer is …". | Rules are stored on the question (bank) and per-step (`required` override is only written when it differs, otherwise `null` = inherit). Conditionals are validated against the **whole survey**: a condition may only reference questions in the **same or an earlier** step — that is what `SurveyConfigValidator` (via `SurveyDefinitionLoader.findProblems`) enforces. |

### Step 5 — **Save changes** (Update step modal)

| Admin | System |
|---|---|
| Presses **Save changes** | `PUT /api/content/surveys/{code}/steps/{stepId}` in one transaction: |

1. Lock survey row; load the step; a **Result step cannot be edited here** (**400 RESULT_STEP_NOT_EDITABLE** — use *Configure*).
2. **Optimistic lock**: `request.revision != step.revision` → **409 STEP_MODIFIED** ("changed by someone else, reload").
3. Name uniqueness again.
4. **Resolve every question**: exists in bank, `ACTIVE` (unless already in this step), not used in another step (**QUESTION_IN_OTHER_STEP**), no duplicates, no unknown codes; all problems are collected and returned **at once** → **400 INVALID_STEP_QUESTIONS**, nothing saved.
5. **Status rule**: cannot go back to `DRAFT` once published (**409 INVALID_STATUS_TRANSITION**); `ACTIVE` needs ≥ 1 visible question (**409 STEP_HAS_NO_QUESTIONS**).
6. **Write the questions**: create/update content in the bank, link into the step in the submitted order, store the `required` override. A **removed** question that already has member answers → link **deactivated** (history kept); nobody answered → link **deleted**.
7. **Re-check the whole survey config**: compares problems *before* vs *after*. Only **newly introduced** problems block → **409 SURVEY_CONFIG_CONFLICT**, nothing saved. Pre-existing problems do not block, so a broken survey stays fixable.
8. `revision++`, `updatedAt`, `updatedBy` — so other admins' stale forms are rejected.

### Step 6 — **Preview** (and Preview-check)

| Admin | System |
|---|---|
| Presses **Preview** | `GET …/preview` → exactly what a member would see: only `ACTIVE` questions and `ACTIVE` options, the real "Step n of m" position among member-visible steps, and a flag telling whether this step is currently **visible to members**. Nothing is saved. |
| Fills the step and presses **Continue** | `POST …/preview/check` runs the **same validation members get** — question type, rules, required, conditional applicability, duplicate/unknown fields — but creates no session and stores nothing. Returns the full error list. |

### Step 7 — **Reorder** and **Save order**

| Admin | System |
|---|---|
| Drags steps into the wanted order, presses **Save order** | `PUT …/steps/order` with **all** step ids. Duplicates → **400 DUPLICATE_STEP**; the list no longer matches the DB (someone added/removed a step) → **409 STEP_ORDER_STALE** (reload instead of overwriting); a Result step anywhere but last → **400 RESULT_STEP_MUST_BE_LAST**. Order is renumbered 1..n and the config re-validated. |

### Step 8 — **Activate** (publish the step)

| Admin | System |
|---|---|
| Opens the **⋮** menu → **Activate** | `PUT …/steps/{id}/status`. A QUESTIONS step needs **≥ 1 active question** → else **409 STEP_HAS_NO_QUESTIONS**. Status moves `DRAFT → ACTIVE` or `ACTIVE ↔ INACTIVE`; **`ACTIVE → DRAFT` is refused** (**409 INVALID_STATUS_TRANSITION** — use *Inactive*). Survey config is re-validated for new problems. From this moment the step is part of the member journey. |

### Step 9 — **Delete** (when needed)

| Admin | System |
|---|---|
| **⋮ → Delete**, confirms | Allowed only if the step is **not ACTIVE**, **not the Result step**, and **no member has answered any of its questions**. Otherwise **409 STEP_ACTIVE** / **RESULT_STEP_NOT_DELETABLE** / **STEP_IN_USE** — deactivate instead. Deleting removes the step **and its question links** (questions stay in the bank) and renumbers the rest. |

### Step 10 — **Configure the Result step** (what the member sees + the fallback)

| Admin | System |
|---|---|
| Presses **Configure** on the Result step | `GET …/result-config` → current config + the list of fitness levels (for the fallback picker). |
| Sets the step name/description and the config: **show level breakdown**, **show plan preview**, **plan duration (1–52 weeks)**, **sessions per week (1–7)**, **minutes per session (10–180)**, **fallback level**. | `PUT …/result-config`: locks the survey, checks the step really is a Result step (**400 NOT_A_RESULT_STEP**), the fallback level must exist (**400 FITNESS_LEVEL_NOT_FOUND**), name unique, then stores `result_config` JSON and bumps the revision. |

> Note: this config does **not** decide the level. It decides **how the result is presented** and **what level is used when scoring is impossible**. The level itself comes from Phase 0.

# PHASE 2 — The member takes the survey

### Step 11 — Landing on the survey

| Member | System |
|---|---|
| Logs in with a fresh account and is taken to the survey (or opens `/survey`). | `SurveyFlow` resolves the session by priority: |

1. An **`IN_PROGRESS`** session exists for this survey code → **reuse it** (continue where they left off).
2. Else the newest session is **`SKIPPED`** → **`resume`**: back to `IN_PROGRESS`, same survey version, **all previous answers kept**.
3. Else the newest session is **`COMPLETED`** and the member did **not** ask to retake → go straight to **`/survey/result`**.
4. Else **`start`**: `POST …/sessions` creates a session on the **ACTIVE** survey version, status `IN_PROGRESS`, pinned to that version. Only **one** `IN_PROGRESS` session per member per survey code — a race returns **409 ACTIVE_SESSION_EXISTS** and the client picks up the existing one.

Because the session is **pinned to a version**, content edits made later never disturb a member who is mid-survey.

### Step 12 — Answering, step by step

| Member | System |
|---|---|
| Types/selects answers, presses **Continue**. | `PUT …/sessions/{id}/steps/{stepCode}` validates the whole step **atomically**: known question codes, no duplicates, `value` present, the question is actually shown in this step, every value passes its **question-type handler** (number range / integer-only, option belongs to the bank, text length…), and **conditions**: an answer for a hidden question is rejected (**QUESTION_NOT_APPLICABLE**). Any error → **400 SURVEY_VALIDATION_FAILED**, "Some answers are invalid. Nothing was saved.", with per-question details. On success the answers are upserted (`null` clears a previous answer), so the member can close the tab and come back. |

Member-side detours the system supports:

- **Skip survey** → `SKIPPED` (answers kept), later **resume** continues from the same place.
- **Back / forward** between steps — answers are already persisted.
- The **Level test** step contains exactly the benchmark questions generated in Phase 0 (one number input per exercise).

### Step 13 — Finish → completion gate

| Member | System |
|---|---|
| Presses **Finish** on the last step. | `POST …/sessions/{id}/complete` — locks the session row FOR UPDATE and **re-validates the entire survey from the DB** (not from the client): every active, applicable question must have a valid answer, and an answer to a question that is no longer applicable must be cleared. Any gap → **400 SURVEY_INCOMPLETE**, session stays `IN_PROGRESS`. Only a fully valid survey gets through. |

# PHASE 3 — The system turns the answers into a level and a plan

This happens **inside the same transaction** as completion, so the member never sees "completed but no result".

### Step 14 — Early level snapshot

`assignBenchmarkLevelIfPresent` reads the answers for every benchmark slot and calls `LevelBenchmarkService.assignLevelFromOnboarding(...)`, which writes the level straight onto `member_profiles.fitness_level`. (This is the quick snapshot; the authoritative result is created in the next step.)

### Step 15 — Scoring (`LevelAssessmentService.assess`)

**Source of truth, in order:**

1. **Survey's own rule set** — if `level_rule_sets` has an `ACTIVE` set for this survey code *and* it validates against the survey → `LevelRuleEvaluator` scores it → `method = RULES`. Total score, outcome level, ladder, per-criterion breakdown and summary all come from the rules.
2. **Otherwise the Content Manager's benchmark table** (`assessFromOnboarding`):
   - For **each configured exercise**: read the member's reps / seconds answer from its slot. **A missing answer means scoring is skipped** (falls through to the fallback) — that is why the sync step in Phase 0 matters.
   - `pointsFor(value, beginnerMax, intermediateMax)` → **1 pt** (≤ beginner max), **2 pts** (≤ intermediate max), **3 pts** (above).
   - `total = Σ points`, `max = N × 3`.
   - **Level lookup**: the ACTIVE level whose `[scoreMin, scoreMax]` contains the total; if that range belongs to an inactive level, the nearest active level is used.
   - **Zero rule**: if **any** exercise has 0 reps / 0 seconds (`isCriticalFailure`) → the member is forced to the **lowest active level**, whatever the total.
   - **Unbalanced rule**: if the best and worst exercise are **≥ 2 points apart** (3 on one, 1 on another) → the member drops **one level**.
   - Builds the **ladder** (rank per active level) and a **breakdown per exercise** with its band label ("20–40 reps", "More than 60 reps", "45–90 sec"…), plus a human summary: *"You scored 6 of 9 points… One exercise was not completed, so you start at the lowest level." / "Your results were uneven, so we placed you one level lower."*
3. **Fallback** — no rule set, invalid rule set, or benchmark cannot be scored → `method = FALLBACK` and the level is the **fallback level configured on the Result step**. If none is configured → `method = NONE` (no level), and the reason (`NO_RULE_SET` / `RULES_INVALID`) is stored for troubleshooting.

### Step 16 — Plan recommendation

`RecommendedPlanService.build(level, desiredDaysPerWeek, resultConfig)`:

- `desiredDaysPerWeek` is read from the member's answer to *"How many days per week do you want to train…"* (falling back to *"training days per week"*), 1–7.
- Matches an **ACTIVE `DailyPlanTemplate`** for that level + that many sessions per week.
- Spreads the sessions across the week (`MON`, `WED`, `FRI`…), repeating the template's session list, and attaches exercise details.
- **Presentation comes from the Result step**: `planDurationWeeks`, `sessionsPerWeek`, `minutesPerSession`, and whether the member may see the breakdown / the plan preview.

### Step 17 — Persist the result

- **One row per session** in `survey_level_results` (`1 session = 1 result`): method, reason, level, total score, breakdown JSON, evaluated at. Re-scoring (after a reopen) **updates the same row** instead of piling up history.
- Session → **`COMPLETED`** with `completedAt`.
- `updateProfileFromSurvey` writes into `member_profiles`: **fitness level**, **weight**, **height**, **gender**, **goal type**, **days_per_week**. If both weight and height are present it computes the **BMI** and inserts the first **`member_body_metrics`** row with the note *"Initial measurement from onboarding survey"* — so the member's progress tracking starts on day one.

# PHASE 4 — The member sees the result, previews and starts the plan

### Step 18 — Result screen (`/survey/result`)

| Member | System |
|---|---|
| Arrives right after finishing. | `GET …/sessions/{id}/result` — only for a `COMPLETED` session (**409 SESSION_NOT_COMPLETED**). If an older session has no stored result, it is scored **once** under a row lock (two parallel requests cannot double-score). |

What the member sees:

- **Level badge** — level name and **"Level k of N"** (rank from the ladder).
- **Level test breakdown** (when `showLevelBreakdown`): total score out of `N × 3`, the summary sentence, and per exercise: the value they achieved, the points, and the band they landed in.
- **Recommended plan card** (when `showPlanPreview`): plan name, weeks, sessions/week, minutes/session, weekly rhythm.

### Step 19 — **Preview training plan**

| Member | System |
|---|---|
| Presses **Preview training plan**. | Opens the preview modal with the stored plan: the weekly rhythm, each session's name, and its exercises with sets / reps / duration. Read-only — nothing is written. |

### Step 20 — **Start my training plan**

| Member | System |
|---|---|
| Presses **Start my training plan**. | `POST …/sessions/{id}/start-plan` — requires `COMPLETED` (**409 SESSION_NOT_COMPLETED**), a scored result (**409 RESULT_NOT_AVAILABLE**), and a plan (**409 PLAN_NOT_AVAILABLE**). Then `activatePlan` writes the **level** and the **sessions per week** to the profile and returns the plan snapshot (name, weeks, sessions/week, minutes/session, rhythm, started at). The member is sent to the dashboard to train. |

### Step 21 — Detours after the result

| Member action | System |
|---|---|
| **Back to level test** | `POST …/reopen`: only a `COMPLETED` session; refuses if another `IN_PROGRESS` session exists (**409 ACTIVE_SESSION_EXISTS**). **Deletes the stored result** (so the next finish re-scores from scratch) and puts the session back to `IN_PROGRESS` with all answers intact. |
| **Retake survey** | Starts a brand-new session on the active version (`retake` flag). The completed session and its result stay in history. |
| Comes back later | The result screen is reusable; the profile already holds the level and the weekly rhythm. |

## Quick reference — who writes what

| Data | Written by | Read by |
|---|---|---|
| Benchmark exercises + 1/2-point thresholds | Content Manager (Phase 0) | Scoring, level-test sync |
| Level names + score ranges | Content Manager (Phase 0) | Scoring (`resolveLevel`), result screen ladder |
| Level test questions (`*_MAX_REPS` / `*_MAX_SECONDS`) | **System**, auto-generated by `BenchmarkSurveySync` | Member's Level test step |
| Survey steps, order, questions, conditions, statuses | Admin/Content Manager (Phase 1) | Member journey |
| `result_config` (breakdown, preview, weeks, sessions, minutes, fallback level) | Admin/Content Manager (Step 10) | Result screen + plan builder + fallback |
| Answers | Member (Phase 2) | Completion gate, scoring, profile sync |
| Level + breakdown + plan | System (Phase 3) | Result screen, preview modal, start-plan |
| `member_profiles` (level, body data, days/week) and the first body metric | System (Step 17 / 20) | Profile, progress tracking, dashboard |

## Error cheat-sheet

| Code | When |
|---|---|
| `STEP_MODIFIED` (409) | Someone else saved the step since the form was opened (revision mismatch). |
| `SURVEY_CONFIG_CONFLICT` (409) | The change would introduce a **new** configuration problem (e.g. a condition pointing at a later step). |
| `INVALID_STATUS_TRANSITION` (409) | Trying to move a published step back to `DRAFT`. |
| `STEP_HAS_NO_QUESTIONS` (409) | Activating a step with no active question. |
| `STEP_ORDER_STALE` (409) | The step list changed since it was loaded. |
| `RESULT_STEP_MUST_BE_LAST` (400) | Reordering the Result step away from the end. |
| `STEP_IN_USE` / `RESULT_STEP_NOT_DELETABLE` (409) | Deleting a step members already answered, or the Result step. |
| `SURVEY_VALIDATION_FAILED` (400) | Bad answers on a step — nothing saved. |
| `SURVEY_INCOMPLETE` (400) | Finishing while a required/applicable question is missing or stale. |
| `ACTIVE_SESSION_EXISTS` (409) | Starting/reopening while another session is already in progress. |
| `SESSION_NOT_COMPLETED` (409) | Asking for a result or starting a plan too early. |
| `PLAN_NOT_AVAILABLE` (409) | No plan could be built for the scored level + days/week. |
